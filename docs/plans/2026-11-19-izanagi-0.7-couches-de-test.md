# Izanagi 0.7, couches de test : plan d'implémentation

> **Exécution :** ce plan s'exécute tâche par tâche, un implémenteur par tâche, chaque tâche relue avant la suivante. Les étapes sont des cases à cocher (`- [ ]`).

**But :** un projet posé a des couches de test unitaire, intégration et fonctionnelle, que `check.sh` lance séparément. Les flux donnent une couche à chaque test et la vérifient en revue, et une passe de mutation sur le diff montre au relecteur les tests qui ne vérifient rien.

**Architecture :** chaque pile reçoit un fragment par couche. `install.sh` lit les couches de chaque composant dans un cinquième champ de `composant=` et rend une étape par couche déclarée, plus une fonction `verifier_<id>_fonctionnelle` que seul `--complet` appelle. `harness.md` liste les couches en lignes `- couche : …` que `check-contract.sh` lit (règles 10 et 11). Un nouveau script, `scripts/mutation.sh`, lance l'outil de mutation de chaque pile sur le diff. `scripts/migrations/0.7.0.sh` met un projet 0.6 à niveau.

**Pile :** Bash (Git Bash sous Windows), skills et sous-agents Claude Code, GitHub Actions, `cargo-mutants`, Stryker, `mutmut`, `cargo-llvm-cov`, Playwright.

**Spec :** `docs/specs/2026-11-19-izanagi-0.7-couches-de-test.md`, décisions 89 à 116.

## Coutures

Les tests passent par ces interfaces, et par elles seules :

- `scripts/install.sh` : les fichiers posés dans un projet vide, `check.sh` et `harness.md` compris.
- `check.sh` rendu : son code de sortie et ses lignes `-- <nom> : <étape>` avec `--host`, `--complet` ou une option inconnue, sur un projet d'essai dont les commandes de test sont remplacées par des faux sur le `PATH`.
- `scripts/check-contract.sh` : sa sortie sur un dépôt d'essai.
- `scripts/doctor.sh` : sa sortie sur un poste dont les outils sont remplacés par des faux.
- `scripts/mutation.sh` : sa sortie sur un dépôt d'essai, avec de faux outils de mutation.
- `scripts/migrations/0.7.0.sh` : les fichiers du projet après le passage, et les lignes affichées.
- `tests/skills.sh` : la structure des skills et des sous-agents, par des recherches de texte.

## Contraintes globales

- Aucun script n'emploie `jq`, Node ou Python. Le JSON s'écrit avec `printf` et se lit avec `json_string`.
- Les noms de couche s'écrivent sans accent dans les scripts et les fichiers `clé=valeur` : `unitaire`, `integration`, `fonctionnelle` (décision 92). La prose écrit « intégration ».
- `mutation.sh` ne fait jamais échouer la vérification ni la CI (décision 112). Il sort avec 0, sauf sur un usage faux (code 2).
- La couverture n'a pas de seuil et ne fait jamais échouer un job (décision 102).
- Aucun commit ne part sur la branche principale hors d'une PR.
- Noms de fichiers en anglais. Contenu et messages en français. Préfixe des messages d'un script : son nom suivi de ` : `.
- Chaque tâche finit avec tous les scripts de `tests/` qui passent, puis `claude plugin validate .`. `tests/tools.sh` prend deux à trois minutes sous Windows : il se lance seul.
- Version finale : `0.7.0` dans `.claude-plugin/plugin.json` et `.claude-plugin/marketplace.json`.

## Points de revue

- `check.sh --complet --host` et `check.sh --host --complet` font la même chose. `check.sh --clean --complet` sort avec 2. Test à la tâche 1.
- Sous Windows avec `linux` en cible, `--complet` passe à la copie WSL : `verifier_wsl` lance `check.sh --host --complet`. Test à la tâche 1, par la commande que reçoit un faux `wsl.exe`.
- Les tests de documentation de Rust. En 0.6, `cargo test --workspace` les lançait. L'étape `unitaire` ne doit pas les perdre : elle lance aussi `cargo test --doc` quand le composant a une cible bibliothèque. Test à la tâche 2.
- Un composant déclaré avec la seule couche `unitaire` n'a ni étape `integration`, ni fonction `verifier_<id>_fonctionnelle`. Test à la tâche 2.
- Un projet dont un composant n'a pas de couche fonctionnelle mais dont l'entrée `fonctionnel` du projet existe : `--complet` lance l'entrée du projet après les composants. Test à la tâche 2.
- Une tranche d'un projet sans couche fonctionnelle (type `library`) n'a pas de ligne `**Acceptation :**`. Le plan le dit, la phase plan ne le réclame pas. Test à la tâche 7.
- Un projet 0.6 dont les tests Python sont à plat dans `tests/`. La migration garde l'ancienne commande comme couche `unitaire`, et liste les fichiers qu'elle ne range pas. La vérification passe juste après la migration. Test à la tâche 11.
- `mutation.sh` sur un diff qui ne touche aucun fichier de code (documentation seule) : `mutation : rien à muter`, code 0. Test à la tâche 9.

## Tranche 1 : couches dans la vérification

**À essayer :** poser un projet cli Rust avec `install.sh`, puis lancer `scripts/check.sh --host` et `scripts/check.sh --host --complet`. La première sortie montre les étapes `unitaire` et `integration`, la seconde ajoute `fonctionnelle`. `check-contract.sh` dit `contrat : respecté`.

**Risque :** élevé. `check.sh` est la vérification de tous les projets posés : une erreur bloque chaque push ou laisse passer un test rouge.

### Tâche 1 : arguments de `check.sh` et `--complet`

**Coutures :** `check.sh` rendu.

**Fichiers :**
- Modifier : `templates/code/scripts/check.sh`, `tests/install.sh`

**Interfaces :**

- `check.sh` lit tous ses arguments. `--host` et `--complet` se combinent dans tout ordre. `--clean` ne se combine avec rien. Tout autre argument, ou `--clean` avec un autre, sort avec 2 et `usage : scripts/check.sh [--host] [--complet] | --clean`, sans rien lancer.
- `verifier_tout` appelle les fonctions `verifier_<id>` des composants. Avec `--complet`, `verifier_tout_complet` appelle ensuite les fonctions `verifier_<id>_fonctionnelle` qui existent, puis `verifier_projet_fonctionnelle` si elle existe. Le gabarit reçoit le marqueur `{{appels_complets}}` pour ces appels.
- `verifier_wsl` lance `check.sh --host`, suivi de `--complet` quand il a été demandé.
- La fin de sortie dit `<système> : tout passe` ou `<système> : tout passe (complet)`.

- [ ] **Étape 1 :** tests rouges dans `tests/install.sh` : un projet rendu avec deux composants, des faux `cargo` et `npm` sur le `PATH` qui affichent leurs arguments. Cas : `--host`, `--host --complet`, `--complet --host`, `--clean --complet` (code 2), `--inconnu` (code 2, aucun faux appelé), et la commande reçue par un faux `wsl.exe`.
- [ ] **Étape 2 :** remplacer le `case "${1:-}"` par une boucle sur les arguments, ajouter `verifier_tout_complet` et la propagation à WSL.

### Tâche 2 : une étape par couche dans les gabarits

**Coutures :** `scripts/install.sh`, `check.sh` rendu.

**Fichiers :**
- Créer : `templates/{rust,typescript,python,core}/fragments/test-unitaire.sh`, `test-integration.sh`, `test-fonctionnelle.sh`
- Modifier : `scripts/install.sh`, `templates/{rust,typescript,python,core}/fragments/check-section.sh`, `templates/core/docs/agents/harness.md`, `templates/core/defaults.env`, `tests/install.sh`

**Interfaces :**

La valeur `composant=` gagne un cinquième champ : `composant=<nom>|<chemin>|<pile>|<lancement>|<couches>`, où `<couches>` est une liste séparée par des virgules, prise parmi `unitaire`, `integration` et `fonctionnelle`. Vide, elle vaut `unitaire`. Une couche inconnue fait sortir `install.sh` avec 1 et `install.sh : couche « <c> » du composant <nom> refusée`.

Une valeur facultative `fonctionnel_projet=<dossier>|<commande>` déclare l'entrée `fonctionnel` du projet (décision 97).

`check-section.sh` d'une pile garde l'installation, le format et le lint, puis reçoit `{{etapes}}` à la place de l'étape `tests`. `install.sh` y rend le fragment `test-unitaire.sh` puis `test-integration.sh`, selon les couches déclarées. Si `fonctionnelle` est déclarée, il rend en plus une fonction `verifier_<id>_fonctionnelle` avec le fragment `test-fonctionnelle.sh`, dans le même sous-shell et le même `cd`. Chaque fragment annonce `echo "-- {{composant}} : <couche>"`.

| Pile | unitaire | integration | fonctionnelle |
|---|---|---|---|
| Rust | `cargo test --workspace --locked --lib --bins`, puis `cargo test --workspace --locked --doc` si le composant a une bibliothèque | `cargo test --workspace --locked --test '*'` | `cargo test --workspace --locked --features fonctionnel --test 'fonctionnel_*'` |
| TypeScript | `npm run test:unitaire` | `npm run test:integration` | `npm run test:fonctionnel` |
| Python | `uv run pytest tests/unitaires` | `uv run pytest tests/integration` | `uv run pytest tests/fonctionnels` |
| autre | `# À ÉCRIRE : {{composant}} ({{pile}}), couche <couche>` | idem | idem |

`fonctionnel_projet` rend `verifier_projet_fonctionnelle`, qui annonce `-- projet : fonctionnelle` et lance la commande à la racine.

`harness.md` remplace la ligne `Couches de test` par une section « Couches de test » : un tableau lisible (composant, couche, dossier, commande) et, dessous, une ligne par couche pour les scripts :

```
- couche : <composant> | <couche> | <dossier> | <commande>
- couche : projet | fonctionnelle | <dossier> | <commande>
```

Les dossiers par pile sont ceux de la décision 94 : Rust `src`, `tests`, `tests/fonctionnel_*.rs` ; TypeScript `src`, `tests/integration`, `tests/fonctionnels` ; Python `tests/unitaires`, `tests/integration`, `tests/fonctionnels`. La clé `couches` de `defaults.env` disparaît.

- [ ] **Étape 1 :** lire les faits Cargo et Vitest, et recopier chacun en commentaire dans le fragment qui s'en sert.
- [ ] **Étape 2 :** tests rouges dans `tests/install.sh` : un composant de chaque pile avec les trois couches, un composant `unitaire` seul (ni étape `integration`, ni fonction fonctionnelle), une couche inconnue (code 1), `fonctionnel_projet` déclaré, les lignes `- couche :` de `harness.md`, une pile sans gabarit (trois `À ÉCRIRE`).
- [ ] **Étape 3 :** écrire les fragments et le rendu dans `install.sh`.
- [ ] **Étape 4 :** tests verts. Commit `feat: une étape par couche de test`.

### Tâche 4 : `--complet`, Playwright et couverture dans la CI

**Coutures :** `scripts/install.sh`, `check.sh` rendu.

**Fichiers :**
- Créer : `templates/core/fragments/ci-playwright.yml`, `templates/{rust,typescript,python}/fragments/ci-couverture.yml`

**Interfaces :**

- Le job `check` lance `bash scripts/check.sh --host --complet`. La règle 7 du contrat attend cette ligne.
- Une valeur `navigateur=oui` (posée par `init` quand une couche fonctionnelle emploie Playwright) ajoute au job `check` le fragment `ci-playwright.yml`, avec `if: matrix.os == 'ubuntu-latest'`. Le job passe `IZANAGI_NAVIGATEUR=non` aux autres systèmes. Une étape fonctionnelle qui emploie Playwright affiche alors `-- <nom> : fonctionnelle : navigateur absent de ce système, sauté` et rend 0.
- Un job `couverture`, sur `ubuntu-latest`, installe les outils de couverture des piles (`ci-couverture.yml`) et lance `IZANAGI_COUVERTURE=1 bash scripts/check.sh --host --complet`. Avec cette variable, les fragments de test mesurent la couverture, et `check.sh` écrit le taux par composant dans `$GITHUB_STEP_SUMMARY` à la fin. Le job a `continue-on-error: true`.
- Sans `IZANAGI_COUVERTURE`, les fragments ne changent pas de commande.
- Les actions ajoutées sont épinglées par SHA, avec l'étiquette en commentaire, comme les autres (décision 50).

### Tâche 9 : `mutation.sh`

**Coutures :** `scripts/mutation.sh`.

**Fichiers :**
- Créer : `scripts/mutation.sh`
- Modifier : `tests/tools.sh`

**Interfaces :**

```
mutation.sh <projet> <point fixe>
```

- Lit `mutation` et `mutation_delai` dans `config.env`. `mutation=non` : affiche `mutation : désactivée` et sort avec 0.
- Calcule `git diff <point fixe>...HEAD` et, pour chaque composant des lignes `- composant :` de `harness.md`, les fichiers du diff sous son chemin. Un composant sans fichier de code dans le diff est sauté. Aucun fichier : `mutation : rien à muter`.
