# Izanagi 0.6, sécurité et auto-amélioration : plan d'implémentation

> **Exécution :** ce plan s'exécute tâche par tâche, un implémenteur par tâche, chaque tâche relue avant la suivante. Les étapes sont des cases à cocher (`- [ ]`).

**But :** un projet posé cherche ses secrets et ses dépendances vulnérables, l'agent demande avant un geste destructeur, et chaque flux laisse des traces qu'une rétrospective transforme en règles, y compris des règles par langage qui remontent au plugin par une PR.

**Architecture :** le découpage d'une commande Bash quitte `guard-push.sh` pour `lib.sh`, et un nouveau hook, `guard-destructive.sh`, s'en sert. Les hooks notent leurs refus dans `.izanagi/refus.log`. Les gabarits reçoivent `gitleaks`, l'audit des dépendances, une CI épinglée, des règles `permissions.deny` et un fichier de règles par langage. Trois skills s'ajoutent : `retro`, `contribuer`, et un sous-agent `reviewer-security`. `scripts/migrations/0.6.0.sh` met un projet 0.5 à niveau.

**Pile :** Bash (Git Bash sous Windows), hooks, skills et sous-agents Claude Code, GitHub CLI, GitHub Actions, `gitleaks`.

**Spec :** `docs/specs/2026-11-18-izanagi-0.6-securite-amelioration.md`, décisions 43 à 80.

## Faits lus

Lus le 2026-11-18. Chaque tâche qui s'en sert les recopie en commentaire, avec la date et l'adresse.

- https://code.claude.com/docs/en/hooks.md : un hook `PreToolUse` qui sort avec 0 et écrit `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "ask", "permissionDecisionReason": "…"}}` fait demander confirmation à l'utilisateur, qui voit la raison. En mode `-p`, personne ne peut répondre : Claude Code refuse l'appel et Claude lit la raison. Le champ `if` d'un hook ne porte qu'une seule règle, sans liste.
- https://code.claude.com/docs/en/permissions.md : les règles `Read` et `Edit` suivent la syntaxe de gitignore. Un motif sans barre (`*.pem`) vaut à toute profondeur sous le dossier courant. Une règle `Read` refusée bloque aussi Edit et Write sur le même chemin, et les commandes de fichier que Claude Code reconnaît dans Bash (`cat`, `head`, `tail`, `sed`, `tee`, redirections). Un motif qui commence par `!` exclut des chemins des règles qui le précèdent dans la même liste. NotebookEdit n'est couvert que par une règle `Edit`.
- https://github.com/gitleaks/gitleaks : `gitleaks git --log-opts="<a>..<b>" <dépôt>` analyse une plage de commits, `--redact` masque les secrets dans la sortie, le code de sortie vaut 1 quand une fuite est trouvée. Un `.gitleaks.toml` avec `[extend]` et `useDefault = true` étend la configuration par défaut. Les exceptions vont dans `[[allowlists]]`, avec `paths` ou `regexes`.

Le hook de la tâche 2 n'a donc à couvrir, pour les fichiers de secrets, que les commandes que Claude Code ne reconnaît pas comme commandes de fichier : `source`, `.`, `cp`, `mv`, `less`, `more`, `base64`, `xxd`, `strings`. Couvrir aussi `cat` et `grep` ne coûte rien et garde la décision 54 entière.

## Coutures

Les tests passent par ces interfaces, et par elles seules :

- `hooks/guard-destructive.sh`, `hooks/guard-push.sh`, `hooks/verify-implementer.sh` : code de retour, sortie standard et sortie d'erreur pour une entrée JSON donnée, et le contenu de `.izanagi/refus.log` après le passage.
- `scripts/lib.sh` : la fonction `commandes_simples`, appelée depuis un test.
- `scripts/refus.sh` : sa sortie sur un projet d'essai.
- `scripts/install.sh` : les fichiers posés dans un projet vide.
- `scripts/doctor.sh` et `scripts/check-contract.sh` : leur sortie sur un dépôt d'essai.
- `scripts/migrations/0.6.0.sh` : les fichiers du projet après le passage, et les lignes affichées.
- `tests/skills.sh` : la structure des skills et des sous-agents, par des recherches de texte.

## Contraintes globales

- Aucun script n'emploie `jq`, Node ou Python. Le JSON s'écrit avec `printf` et se lit avec `json_string`.
- Chaque hook sort avec 0, sans rien écrire, hors d'un projet Izanagi.
- Les valeurs écrites dans un fichier `clé=valeur` sont en ASCII quand un script les compare : `hook_destructif` vaut `demande`, `bloque` ou `avertit`.
- Aucune PR et aucune issue ne s'ouvrent sans l'accord de l'utilisateur, sauf l'issue du job hebdomadaire de sécurité (décision 48).
- `retro` ne modifie ni le plugin, ni `hooks.json`, ni les clés `hook_*` (décision 64).
- Aucun commit ne part sur la branche principale hors d'une PR.
- Noms de fichiers en anglais, sauf `references/langages/` et `docs/standards/`, que la spec nomme. Contenu et messages en français. Préfixe des messages d'un script : son nom suivi de ` : `.
- Chaque tâche finit avec tous les scripts de `tests/` qui passent, puis `claude plugin validate .`. `tests/tools.sh` prend deux à trois minutes sous Windows : il se lance seul.
- Version finale : `0.6.0` dans `.claude-plugin/plugin.json` et `.claude-plugin/marketplace.json`.

## Points de revue

- Un message de commit qui cite une commande destructrice, `git commit -m "doc: git reset --hard"`. Le hook laisse passer : le texte entre guillemets est un mot, pas une commande. Test à la tâche 2.
- `git push --force-with-lease` et `git push -f` vers une branche de travail. Le premier passe, le second demande. Un `+ref` dans la liste des références compte comme `--force`. Test à la tâche 2.
- `rm -rf node_modules` dans le dépôt passe. `rm -rf ..`, `rm -rf ~/x`, `rm -rf "$DOSSIER"` et `rm -rf .` lancé depuis la racine demandent. Une cible avec `$` ou un accent grave compte comme hors du dépôt, puisque le hook ne peut pas la résoudre. Test à la tâche 2.
- `cat .env.example` passe, `source .env.local` demande, `cat .envrc` demande aussi : le motif `.env*` le couvre, et le README le dit. Test à la tâche 2.
- Un clone sans la branche principale en local, comme le checkout d'une CI. `check.sh` analyse alors la plage `origin/<branche>..HEAD`, et tout l'historique si aucune des deux références n'existe, avec une ligne qui le dit. Test à la tâche 4.
- Un projet 0.5 dont `.claude/settings.json` porte déjà d'autres clés. La migration ne l'écrit pas : elle affiche `à fusionner .claude/settings.json`, et `upgrade` ajoute les règles avec l'outil Edit. Test à la tâche 12.

### Tâche 2 : hook `guard-destructive.sh` et `refus.log`

**Coutures :** `hooks/guard-destructive.sh`, `hooks/guard-push.sh`, `hooks/verify-implementer.sh`, `scripts/lib.sh`.

**Fichiers :**
- Créer : `hooks/guard-destructive.sh`
- Modifier : `scripts/lib.sh`, `hooks/guard-push.sh`, `hooks/verify-implementer.sh`, `hooks/hooks.json`, `tests/hooks.sh`

**Interfaces :**

```
refus_noter <racine> <hook> <motif>
```

- Ajoute à `<racine>/.izanagi/refus.log` la ligne `<date ISO 8601>|<branche courante>|<hook>|<motif>`. Les `|` et les sauts de ligne du motif deviennent des espaces. N'échoue jamais : une écriture ratée ne change pas la décision du hook.
- `<hook>` vaut `push`, `verification` ou `destructif`.
- `guard-push.sh` note chaque refus et chaque avertissement. `verify-implementer.sh` note chaque vérification rouge, avec le motif `vérification rouge` ou `vérification rouge après deux refus`.

`guard-destructive.sh` lit `tool_input.command`, sort avec 0 au-delà de 20 000 caractères avec le même avertissement que `guard-push.sh`, puis examine chaque commande simple. Elle est visée dans ces cas :

| Commande | Visée quand | Motif |
|---|---|---|
| `git reset` | un mot vaut `--hard` | `git reset --hard` |
| `git clean` | un mot vaut `--force` ou est une option courte qui contient `f` | `git clean -f` |
| `git push` | un mot vaut `--force` ou `-f`, ou une référence commence par `+`, et aucun mot ne commence par `--force-with-lease` | `git push --force` |
| `git branch` | un mot vaut `-D`, ou les mots contiennent `--delete` et `--force` | `git branch -D` |
| `git checkout`, `git restore` | un mot vaut `.` et `git status --porcelain` n'est pas vide | `<commande> .` sur un arbre modifié |
| `rm` | les options demandent la récursion (`-r`, `-R`, `--recursive`) et la force (`-f`, `--force`), et une cible vaut la racine du dépôt ou résout hors de lui | `rm -rf <cible>` |
| `cat`, `less`, `more`, `head`, `tail`, `grep`, `source`, `.`, `cp`, `mv`, `base64`, `xxd`, `strings` | un argument a pour nom de fichier `.env*` sauf `.env.example`, `*.pem`, `*.key`, `id_rsa*` ou `credentials*` | `lecture de <fichier>` |

Pour `rm`, `~` en tête de cible devient `$HOME`. Une cible qui contient `$` ou un accent grave compte comme hors du dépôt. Une cible relative se résout depuis le dossier `cwd` de l'entrée.

Réponse selon `hook_destructif` (absent : `demande`) :

- `demande` : sortie standard `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "ask", "permissionDecisionReason": "Izanagi : <motif>. Confirme si c'est voulu."}}`, code 0.
- `bloque` : sortie d'erreur `Izanagi : <motif> refusé. Pour être consulté à la place, mets hook_destructif=demande dans .izanagi/config.env.`, code 2.
- `avertit` : sortie standard `{"systemMessage": "Izanagi : <motif>."}`, code 0.

`hooks.json` déclare le hook dans `PreToolUse`, filtre `Bash`, sans champ `if` : le champ ne prend qu'une règle, et le hook vise plusieurs programmes.

- [ ] **Étape 1 :** tests dans `tests/hooks.sh`, un par ligne de la table, plus les cas des points de revue (message de commit, `--force-with-lease`, `+ref`, `rm -rf node_modules`, `rm -rf ..`, `rm -rf ~/x`, `rm -rf "$DOSSIER"`, `rm -rf .` à la racine, `.env.example`, `.envrc`), les trois valeurs de `hook_destructif`, la clé absente, un dossier hors projet Izanagi, une commande de plus de 20 000 caractères. Pour chaque cas visé, le test lit la dernière ligne de `refus.log`. Tests de `refus_noter` sur `guard-push.sh` et `verify-implementer.sh`.
- [ ] **Étape 2 :** tests rouges.
- [ ] **Étape 3 :** écrire `refus_noter` dans `lib.sh`, `guard-destructive.sh`, et brancher les deux autres hooks. Le commentaire d'en-tête du hook recopie les faits lus sur `ask` et dit que c'est un garde-fou contre l'habitude (décision 56).

### Tâche 5 : CI épinglée, audit des dépendances, job hebdomadaire

**Coutures :** `scripts/install.sh`, `scripts/doctor.sh`.

**Fichiers :**
- Créer : `templates/rust/fragments/ci-audit.yml`, `templates/typescript/fragments/ci-audit.yml`, `templates/python/fragments/ci-audit.yml`, `templates/core/fragments/ci-audit.yml`, `templates/code/.github/dependabot.yml`, `templates/code/.github/workflows/securite.yml`
- Modifier : `templates/code/.github/workflows/ci.yml`, les `ci-setup.yml` des trois piles, `scripts/install.sh`, `scripts/doctor.sh`, `references/verification-contract.md`, `scripts/check-contract.sh`, `tests/install.sh`, `tests/tools.sh`

**Interfaces :**

- Chaque `uses:` des gabarits s'écrit `<action>@<SHA de 40 caractères> # <étiquette>`. La tâche lit chaque SHA avec `gh api repos/<propriétaire>/<action>/commits/<étiquette> --jq .sha` et note la date de lecture en commentaire de tête de `ci.yml`.
- Le checkout prend `persist-credentials: false` et `fetch-depth: 0`, pour que `gitleaks` voie la plage.
- `ci.yml` installe `gitleaks` avant `check.sh`, depuis la page des versions, à une version fixée et vérifiée par sa somme SHA-256.
- `ci.yml` reçoit un job `audit` qui rend le fragment `ci-audit.yml` de chaque pile, par une nouvelle valeur `{{ci_audit}}` d'`install.sh`, construite comme `ci_setup`. Les commandes : `cargo audit` (Rust), `npm audit --audit-level=high` (TypeScript), `pip-audit` sur la sortie de `uv export --format requirements-txt` (Python). Le fragment du cœur porte `# À ÉCRIRE`.
- **À trancher par l'utilisateur avant l'étape 2 :** la décision 47 veut un échec sur une faille haute ou critique et un avertissement sur une faille moindre. La tâche vérifie dans la documentation de `cargo audit` et de `pip-audit` qu'ils savent filtrer par gravité. S'ils ne le savent pas, elle s'arrête et propose à l'utilisateur soit l'échec sur toute faille connue pour ces deux piles, soit un outil qui filtre (`osv-scanner`).
- `securite.yml` : déclencheurs `schedule` (lundi, 6 h UTC) et `workflow_dispatch`, `permissions: contents: read` au niveau du fichier, et un job qui ajoute `issues: write`. Le job lance l'audit et `gitleaks git` sur tout l'historique, en continuant après un échec. S'il y a un échec, il cherche une issue ouverte avec l'étiquette `securite` (`gh issue list --label securite --state open`), la commente avec la fin des sorties, ou la crée sous le titre `Sécurité : contrôle hebdomadaire en échec`, et le job échoue.
- `dependabot.yml` : écosystème `github-actions`, dossier `/`, fréquence hebdomadaire.
- `doctor.sh` : `écart   actions épinglées : <fichier>:<ligne> <action>` pour chaque `uses:` de `.github/workflows/*.yml` qui ne finit pas par `@` suivi de 40 caractères hexadécimaux. `ok      actions épinglées` sinon, ou sans dossier `.github/workflows`.
- `check-contract.sh` signale un `ci.yml` dont le job `audit` garde `# À ÉCRIRE`.

- [ ] **Étape 1 :** tests rouges : `tests/install.sh` (les quatre fichiers posés, aucun `uses:` sans SHA, le fragment de chaque pile rendu, `{{ci_audit}}` remplacé) et `tests/tools.sh` (contrôle `actions épinglées` sur une action épinglée et une non épinglée).
