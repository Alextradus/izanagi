# Izanagi 0.4, état et hooks : plan d'implémentation

> **Exécution :** ce plan s'exécute tâche par tâche, un implémenteur par tâche, chaque tâche relue avant la suivante. Les étapes sont des cases à cocher (`- [ ]`).

**But :** un projet Izanagi garde ses réglages et l'état de son flux dans `.izanagi/`, trois hooks appliquent les règles que les skills décrivaient, et `status`, `doctor` et `upgrade` rejoignent `init` et `jalon`.

**Architecture :** `scripts/lib.sh` lit les fichiers `clé=valeur`. `scripts/state.sh` est le seul à écrire `.izanagi/state.env`. Trois scripts de `hooks/` lisent `config.env` et `state.env` sans passer par le modèle, et sortent sans rien faire hors d'un projet Izanagi. `scripts/migrations/<version>.sh` porte chaque migration, que `upgrade` enchaîne. Les skills lisent `.izanagi/config.env` à la place de `docs/agents/jalon.md`.

**Pile :** Bash (Git Bash sous Windows), hooks et skills Claude Code, GitHub CLI.

**Spec :** `docs/specs/2026-11-12-izanagi-harness-design.md`, décisions D2, D11 à D19, D23 à D25, la deuxième ligne de D28, et D32 à D36.

## Coutures

- `scripts/state.sh <commande>`, sorties et codes de retour. Les tests observent le fichier `.izanagi/state.env` et la sortie standard.
- Chaque script de `hooks/` : JSON sur l'entrée standard, code de retour, sortie standard et sortie d'erreur.
- `scripts/status.sh`, `scripts/doctor.sh <projet>` et `scripts/migrations/0.4.0.sh <projet>` : sortie standard, code de retour, fichiers du projet après le lancement.
- `scripts/install.sh <projet> <fichier-valeurs>`, déjà testé par `tests/install.sh`.

## Contraintes globales

- Aucun script n'emploie `jq`, Node ou Python. Bash et les outils de Git Bash suffisent (D11, question 20 de l'entretien).
- Un hook lancé hors d'un projet Izanagi sort avec 0 sans rien écrire. Un projet Izanagi est un dépôt git dont la racine contient `.izanagi/config.env`. Le plugin est actif dans tous les projets de l'utilisateur.
- Un hook ne lit jamais `config.env` ou `state.env` avec `source`. Les valeurs contiennent des espaces et des accents graves.
- Les clés sont en minuscules, `^[a-z_]+$` (D34).
- Seul `scripts/state.sh` écrit `state.env` (D13). Aucun skill ne l'écrit avec Write ou Edit.
- Noms de fichiers en anglais, contenu et messages en français. Préfixe des messages : le nom du script suivi de ` : `.
- `install.sh` n'écrase jamais un fichier existant.
- Chaque tâche finit avec tous les scripts de `tests/` qui passent, puis `claude plugin validate .`.
- Version finale : `0.4.0` dans `.claude-plugin/plugin.json`.

## Points de revue

- Une commande `git push` qui pousse un tag depuis la branche principale (`git push origin v1.2.0`, `git push --tags`). Le hook doit la laisser passer : la clôture d'un jalon pousse son tag ainsi. Test à la tâche 4.
- `git push` sans argument depuis une branche de flux, puis depuis la branche principale. Seul le second est refusé. Test à la tâche 4.
- Une valeur de `config.env` qui contient `=`, une espace ou un accent grave (`decisions=la section « Décisions » de la spec`, `hors_revue`). `config_get` rend la valeur entière, après le premier `=`. Test à la tâche 1.
- Un implémenteur qui rend « bloqué » avec une vérification rouge. Le hook le laisse s'arrêter (D35). Test à la tâche 5.
- Une vérification qui échoue trois fois de suite pour le même sous-agent. Le hook bloque deux fois, puis laisse passer avec un avertissement (D35). Test à la tâche 5.
- Un projet posé en 0.3 dont `docs/agents/jalon.md` a été modifié à la main (une valeur changée, une ligne ajoutée). La migration reprend les valeurs qu'elle sait lire, liste les lignes qu'elle n'a pas reconnues et ne supprime `jalon.md` que si elle les a toutes lues. Test à la tâche 7.

### Tâche 1 : `lib.sh` et `state.sh`

**Coutures :** `scripts/state.sh`.

**Fichiers :**
- Créer : `scripts/lib.sh`, `scripts/state.sh`, `tests/state.sh`

**Interfaces :**
- Produit, dans `lib.sh`, à charger avec `. "$(dirname "$0")/lib.sh"` :
  - `project_root` : affiche la racine git du dossier courant, ou sort avec 1 s'il n'y a pas de dépôt.
  - `kv_get <fichier> <clé>` : affiche la valeur de la dernière ligne `clé=…` du fichier, tout ce qui suit le premier `=`, sans le retour chariot final. N'affiche rien et rend 1 si la clé manque ou si le fichier manque. Ignore les lignes vides et celles qui commencent par `#`.
  - `config_get <clé>` et `state_get <clé>` : `kv_get` sur `.izanagi/config.env` et `.izanagi/state.env` de la racine.
  - `plugin_version` : la valeur de `"version"` dans `.claude-plugin/plugin.json` du plugin.
  - `version_lt <a> <b>` : rend 0 si `a` précède `b`, en comparant trois nombres séparés par des points.
- Produit, `state.sh` :
  - `state.sh start <flux> <nom>` : `<flux>` vaut `jalon`, `task` ou `fix`, `<nom>` suit `^[a-z0-9][a-z0-9-]*$`. Écrit `flux`, `nom`, `phase=cadrage` pour un jalon ou `phase=debut` sinon, et `maj=<date ISO UTC>`. Refuse avec le code 2 si `state.env` existe déjà.
  - `state.sh set <clé>=<valeur>…` : clés permises `phase`, `tranche`, `tour`, `plan`. `phase` vaut `cadrage`, `plan`, `tranches`, `revue`, `test`, `cloture` ou `debut`. `tranche` et `tour` sont des entiers. Une clé ou une valeur refusée sort avec 2 sans rien écrire. Met `maj` à jour.
  - `state.sh get [clé]` : sans clé, affiche le fichier. Sort avec 1 et n'affiche rien s'il n'y a pas d'état.
  - `state.sh clear` : supprime `state.env`. Sort avec 0 même s'il n'existe pas.
  - Option `--commit`, acceptée par `start`, `set` et `clear` : après l'écriture, `git add` du seul `state.env` puis `git commit -m "chore(izanagi): état <flux> <nom>, <phase>"`. Sans changement à commiter, ne commite pas et sort avec 0.
  - L'écriture passe par un fichier temporaire du même dossier, puis `mv`.
  - Hors d'un projet Izanagi (`.izanagi/config.env` absent), toute commande sort avec 2 et le message `state.sh : pas un projet Izanagi`.

### Tâche 4 : refus du push sur la branche principale

**Coutures :** `hooks/guard-push.sh`.

**Fichiers :**
- Créer : `hooks/guard-push.sh`
- Modifier : `tests/hooks.sh`

**Interfaces :**
- Consomme : l'entrée standard du hook `PreToolUse`, un JSON dont `tool_input.command` porte la commande. Le script ne décode pas le JSON : il cherche ses motifs dans le texte brut.
- Produit : la commande vise la branche principale quand l'une de ces conditions est vraie, `<b>` étant la valeur de `branche` dans `config.env` :
  - un mot de la commande, après `git push`, vaut `<b>`, ou finit par `:<b>`, ou vaut `refs/heads/<b>` ;
  - la commande ne nomme aucune référence après le dépôt distant (`git push`, `git push origin`, `git push -u origin`), et la branche courante est `<b>`.

  Une commande qui porte `--tags`, `--delete` ou `-d`, ou dont la seule référence commence par `v` suivi d'un chiffre ou par `refs/tags/`, ne vise pas la branche principale.

  Quand la commande vise la branche principale :
  - avec `hook_push=bloque` : code 2, et sur la sortie d'erreur `Izanagi : push direct sur <b> refusé. Passe par une PR. Pour l'autoriser, mets hook_push=avertit dans .izanagi/config.env.` ;
  - avec `hook_push=avertit` : code 0, et sur la sortie standard `{"systemMessage": "Izanagi : push direct sur <b>."}`.

  Sinon, code 0 et sortie vide.

- [ ] **Étape 1 : tests en échec.** Une fonction `entree_push <commande>` écrit `{"tool_name":"Bash","tool_input":{"command":"<commande>"}}`. Cas, avec `branche=main` :
  - refusés depuis une branche `task/x` : `git push origin main`, `git push origin HEAD:main`, `git push -f origin task/x:main`, `git push origin refs/heads/main`, `cd sub && git push origin main` ;
  - refusé depuis `main` : `git push`, `git push origin`, `git push -u origin` ;
  - passent depuis `main` : `git push origin v1.2.0`, `git push --tags`, `git push origin refs/tags/v1.2.0`, `git push origin --delete jalon/essai` ;
  - passent depuis `task/x` : `git push`, `git push -u origin task/x`, `git push origin maintenance` (le mot `maintenance` ne vaut pas `main`) ;
  - `hook_push=avertit` : `git push origin main` sort avec 0 et un `systemMessage` ;
  - `branche=trunk` : `git push origin trunk` refusé, `git push origin main` passe ;
  - hors projet Izanagi : `git push origin main` passe.
