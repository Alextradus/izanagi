# Izanagi 0.8, release et livraison : plan d'implémentation

> **Exécution :** ce plan s'exécute tâche par tâche, un implémenteur par tâche, chaque tâche relue avant la suivante. Les étapes sont des cases à cocher (`- [ ]`).

**But :** un projet posé sort une version. Un tag poussé donne une release GitHub avec les notes tirées de `CHANGELOG.md` et le livrable du type d'application, et un workflow lancé à la main déploie un tag. Le projet reçoit aussi un template de PR, Dependabot pour ses dépendances et une analyse Semgrep en CI.

**Architecture :** `install.sh` rend trois gabarits de plus dans `templates/code/` : `release.yml`, `deploiement.yml` (seulement quand le projet a une commande de déploiement) et `scripts/notes-de-version.sh`, qui extrait la section d'une version de `CHANGELOG.md`. Le livrable vient de fragments par pile (`release-version.yml`, `release-binaires.yml`, `release-registre.yml`) que `install.sh` choisit selon `type` et la pile de chaque composant. `dependabot.yml` devient un gabarit rendu par composant. `ci.yml` et `securite.yml` gagnent un job `analyse`. `check-contract.sh` gagne les règles 12 et 13. Les skills `jalon` et `fix` écrivent la section du changelog, poussent le tag et proposent le déploiement. `scripts/migrations/0.8.0.sh` met un projet 0.7 à niveau.

**Pile :** Bash (Git Bash sous Windows), skills Claude Code, GitHub Actions, `gh`, Semgrep CE, Dependabot, crates.io, npm, PyPI.

**Spec :** `docs/specs/2026-11-20-izanagi-0.8-release-livraison.md`, décisions 117 à 140.

## Faits à lire

La tâche qui se sert d'un fait le lit dans la documentation, le recopie en commentaire avec la date et l'adresse, et adapte la commande s'il diffère. Les faits marqués « vérifié » l'ont été le 2026-11-20 pendant l'écriture du plan.

- **npm, tâche 2, vérifié.** La publication de confiance demande npm 11.5.1 ou plus et Node 22.14.0 ou plus, `id-token: write`, un runner hébergé par GitHub, et un `npm publish` sans jeton. Le nom du fichier de workflow s'enregistre sur npmjs.com (https://docs.npmjs.com/trusted-publishers).
- **PyPI et uv, tâche 2, vérifié.** `uv build` écrit dans `dist/`. `uv publish` n'a besoin d'aucun identifiant depuis GitHub Actions avec un éditeur de confiance déclaré sur PyPI, et le job porte `id-token: write` (https://docs.astral.sh/uv/guides/package/).
- **crates.io, tâche 2.** L'action `rust-lang/crates-io-auth-action` donne un jeton dans sa sortie `token` et le révoque à la fin du job. À vérifier : `id-token: write` et le passage `CARGO_REGISTRY_TOKEN: ${{ steps.auth.outputs.token }}` à `cargo publish`.
- **Version d'un composant, tâche 2.** La sortie de `cargo pkgid` (forme `…#<nom>@X.Y.Z` ou `…#X.Y.Z`) et `uv version --short`.
- **Actions de construction, tâche 2.** Les SHA de `actions/upload-artifact`, `actions/download-artifact` et `actions/setup-node` à épingler, et `actions/checkout` avec `ref:` égal à un tag.
- **`workflow_dispatch`, tâche 3, vérifié.** Une entrée `type: string`, lue par le contexte `inputs`. Le workflow doit être sur la branche par défaut.
- **`gh release create`, tâche 2, vérifié.** `gh release create "$TAG" --verify-tag --notes-file <fichier> <fichiers>…`, avec `GH_TOKEN` dans l'environnement. `--verify-tag` arrête la commande si le tag n'existe pas.
- **Dependabot, tâche 4, vérifié.** `uv` est un `package-ecosystem` accepté. Un groupe s'écrit `groups: <nom>: update-types: ["minor", "patch"]`.
- **Semgrep CE, tâche 5, vérifié en partie.** `semgrep scan --config p/default --metrics=off` marche avec les règles du registre, `--severity ERROR` filtre et `--error` fait sortir 1 sur un constat. À vérifier : l'installation en CI (`pipx install semgrep==<version>`) et la dernière version à épingler.
- **Semgrep et Bash, tâche 10, vérifié.** Bash est une langue expérimentale de Semgrep Code. Izanagi, écrit en Bash, ne reçoit donc pas de job `analyse` (décision 138).

## Coutures

Les tests passent par ces interfaces, et par elles seules :

- `scripts/install.sh` : les fichiers posés dans un projet vide, `release.yml`, `deploiement.yml`, `dependabot.yml` et `ci.yml` compris.
- `scripts/notes-de-version.sh` rendu : sa sortie et son code de sortie sur un `CHANGELOG.md` d'essai.
- `scripts/check-contract.sh` : sa sortie sur un dépôt d'essai.
- `scripts/migrations/0.8.0.sh` : les fichiers du projet après le passage, et les lignes affichées.
- `tests/skills.sh` : la structure des skills, par des recherches de texte.

## Contraintes globales

- Aucun script du plugin n'emploie `jq`, Node ou Python. Les workflows posés dans un projet peuvent lancer les outils de sa pile (`node`, `uv`, `cargo`).
- Une valeur `${{ … }}` venue d'une entrée (`inputs.tag`, `github.ref_name`) ne s'écrit jamais dans un `run:`. Elle passe par `env:` et le script lit la variable.
- Chaque action d'un workflow posé est épinglée par SHA, avec l'étiquette en commentaire. Chaque job déclare ses permissions, et le workflow a `permissions: {}` en tête.
- Le changelog suit Keep a Changelog : une section `## [X.Y.Z] - AAAA-MM-JJ` par version, rubriques `### Ajouté`, `### Modifié`, `### Corrigé`, `### Retiré`, et une section `## [Non publié]` facultative en tête.
- Le tag d'une version s'écrit `vX.Y.Z`.
- Les valeurs `type` sont les identifiants des fiches de `references/types/` : `api`, `cli`, `data-ml`, `desktop`, `game`, `library`, `mobile`, `plugin`, `web-frontend`.
- Aucun commit ne part sur la branche principale hors d'une PR.
- Noms de fichiers en anglais, sauf les scripts posés dans un projet, nommés en français comme `check.sh` et `dev.sh` le sont par leur rôle. Contenu et messages en français. Préfixe des messages d'un script : son nom suivi de ` : `.
- Chaque tâche finit avec tous les scripts de `tests/` qui passent, lancés un par un (ils partagent des dossiers temporaires), puis `claude plugin validate .`.
- Version finale : `0.8.0` dans `.claude-plugin/plugin.json` et `.claude-plugin/marketplace.json`.

## Points de revue

- Un tag poussé sans section dans `CHANGELOG.md`, ou sans `CHANGELOG.md`. `notes-de-version.sh` sort avec 1 et `notes-de-version.sh : CHANGELOG.md n'a pas de section [X.Y.Z]`, et `release.yml` échoue avant de publier quoi que ce soit. Test à la tâche 1.
- La section de la plus ancienne version, en fin de fichier, sans section après elle : l'extraction va jusqu'à la fin. La section `## [Non publié]` n'est jamais prise pour une version. Test à la tâche 1.
- Une commande de déploiement qui contient des guillemets, `$` ou `{{`. `deploiement.yml` la lance telle quelle, dans un bloc `run: |`. Test à la tâche 3.
- Un tag passé à `deploiement.yml` qui n'est pas de la forme `vX.Y.Z` (`main; rm -rf /`). Le workflow le lit par `env:`, contrôle sa forme et s'arrête avant le checkout. Test à la tâche 3.
- Un projet à deux composants de piles différentes (cli en Rust et en Python, ou library en TypeScript et en Python). Chaque composant a son livrable dans `release.yml`, et la version se lit dans le composant de `version_composant`. Test à la tâche 2.
- Un composant à la racine (`chemin` vaut `.`). `dependabot.yml` écrit `directory: "/"`, pas `"/."`. Test à la tâche 4.

### Tâche 2 : `release.yml` et livrable par type

**Coutures :** `scripts/install.sh`.

**Fichiers :**
- Créer : `templates/code/.github/workflows/release.yml`, `templates/{rust,typescript,python,core}/fragments/release-version.yml`, `templates/rust/fragments/release-binaires.yml`, `templates/{rust,typescript,python}/fragments/release-registre.yml`, `templates/core/fragments/release-livrable.yml`
- Modifier : `scripts/install.sh`, `templates/core/defaults.env`, `tests/install.sh`

**Interfaces :**

Une valeur `version_composant=<nom>` dit quel composant porte la version du projet. Absente, elle vaut le premier composant. Un nom inconnu fait sortir `install.sh` avec 1 et `install.sh : version_composant « <nom> » n'est pas un composant`.

`release.yml` part au push d'un tag `v*`. Il a `permissions: {}` en tête et ces jobs :

- `verifier` (`contents: read`) : checkout du tag, lecture de la version du composant `version_composant` par le fragment `release-version.yml` de sa pile, puis contrôle `v<version>` égal au tag. Sinon `::error::release.yml : le tag <tag> ne vaut pas la version <version> du fichier de version`, code 1. Il lance ensuite `bash scripts/notes-de-version.sh <version> > notes.md` et téléverse `notes.md`.
- `binaires` (`contents: read`), pour chaque composant Rust d'un projet `cli` : une matrice sur les systèmes de `systemes`, `cargo build --release --locked` dans le dossier du composant, une archive `<composant>-<tag>-<système>.tar.gz` des exécutables de `target/release`, téléversée.
- `publier` (`contents: read`, `id-token: write`), pour chaque composant d'un projet `library`, et chaque composant TypeScript ou Python d'un projet `cli` : le fragment `release-registre.yml` de sa pile. Rust : `crates-io-auth-action` puis `cargo publish --locked`. TypeScript : `setup-node` avec une version de npm qui permet la publication de confiance, `npm ci`, `npm publish`. Python : `uv build`, `uv publish`.
- `livrable` (`contents: read`), pour un type `desktop`, `game`, `mobile` ou `data-ml` : le fragment `release-livrable.yml` du cœur, une étape `# À ÉCRIRE : livrable de <type>` qui sort avec 1 et `::error::release.yml : le livrable de <type> est à écrire`.
- `release` (`contents: write`), après les autres jobs : télécharge `notes.md` et les archives, puis `gh release create "$TAG" --verify-tag --notes-file notes.md <archives>`.

`api`, `web-frontend` et `plugin` n'ont que `verifier` et `release` (décision 126). Une pile sans gabarit a un `release-version.yml` du cœur qui sort avec 1 et `::error::release.yml : lecture de la version à écrire pour <pile>`. Le tag passe aux scripts par `env: TAG: ${{ github.ref_name }}`.

| Pile | `release-version.yml` |
|---|---|
| Rust | `cargo pkgid`, version après le dernier `@` ou `#` |
| TypeScript | `node -p "require('./package.json').version"` |
| Python | `uv version --short` |

- [ ] **Étape 1 :** lire les faits crates.io, version d'un composant, actions de construction et `gh release create`. Recopier chacun en commentaire dans le fragment qui s'en sert.
- [ ] **Étape 2 :** tests rouges dans `tests/install.sh`. Cas : cli Rust sur `linux,windows` (job `binaires` à deux systèmes, pas de job `publier`), library Python (job `publier` avec `id-token: write`, pas de `binaires`), cli à deux composants Rust et Python (`binaires` pour l'un, `publier` pour l'autre), api TypeScript (`verifier` et `release` seuls), type `game` (job `livrable` avec `À ÉCRIRE`), pile `go` (lecture de version à écrire), `version_composant` inconnu (code 1). Dans chaque cas : `permissions: {}` en tête, une ligne `permissions:` par job, aucune action sans SHA, aucun `${{` dans un `run:`.
- [ ] **Étape 3 :** écrire les fragments et le rendu dans `install.sh`.
- [ ] **Étape 4 :** tests verts. Commit `feat: release.yml publie le livrable du type d'application`.
