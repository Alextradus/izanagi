# Izanagi 0.8 : release et livraison

Décisions prises le 2026-11-20 lors d'un entretien (grilling). Elles font foi pour la version 0.8. Elles continuent la numérotation de `2026-11-19-izanagi-0.7-couches-de-test.md`. Les specs précédentes restent valables pour tout ce que celle-ci ne change pas. Une décision qui en modifie une ancienne le dit et donne son numéro.

## But

La 0.8 permet à un projet posé par Izanagi de sortir une version : un changelog, une release GitHub, un livrable publié et un déploiement lancé à la main. Elle ajoute aussi un template de PR, les mises à jour des dépendances du code et une analyse statique de sécurité en CI.

En 0.7, la version monte déjà selon `references/versions.md` : le patch à chaque PR hors jalon, la mineure à la clôture d'un jalon, qui pose le tag sur le commit de fusion. Rien ne vient après le tag. Le projet n'a ni changelog, ni release GitHub, ni livrable, ni déploiement. Le `dependabot.yml` du gabarit ne suit que les actions de la CI. La sécurité repose sur `gitleaks`, l'audit des dépendances et `reviewer-security` au risque élevé, sans outil d'analyse statique.

## Décisions

### Périmètre et livraison

117. La 0.8.0 sort avec un plan dans `docs/plans/` et une PR relue par la revue convergente, comme les versions précédentes (décision 89).
118. La 1.0 est la version où le harnais mène un projet de son cadrage jusqu'à une version publiée et livrée. Ce que la 0.8 n'ajoute pas passe en 1.x et ne retarde pas la 1.0.
119. La 1.0 sort après un projet mené de bout en bout sur la dernière version avant la 1.0 (modifie la décision 90). Ce projet démarre sur la 0.7 et y fait la réception de la 0.7 (issues #27 à #31). Il passe en 0.8 par `/izanagi:upgrade`, ce qui essaie la migration 0.8.0. Sa première release sert de réception à la 0.8.
120. La 0.8 a deux parties. La partie release et livraison couvre le changelog, la release, le livrable, le déploiement et le template de PR. La partie dépendances et analyse couvre Dependabot pour le code et l'analyse statique.

### Changelog et release

121. Le changelog s'écrit au moment de la release. La clôture du jalon lit les PR fusionnées depuis le dernier tag et écrit la section de la version dans `CHANGELOG.md`, au format Keep a Changelog, avec les rubriques Ajouté, Modifié, Corrigé et Retiré. Chaque ligne dit ce qui change pour l'utilisateur du projet, pas le titre d'un commit. La clôture montre la section à l'utilisateur, puis la commite sur la branche du jalon, avant la fusion. Le fichier naît à la première release.
122. `config.env` reçoit la clé `langue_publique`, langue du changelog et des notes de version. L'entretien d'`init` la demande, avec `fr` par défaut.
123. Chaque tag donne une release GitHub. La clôture d'un jalon pose le tag, comme en 0.7. La clôture d'un `fix` demande « publier ce correctif ? » avant la fusion. Sur un oui, elle écrit la section du patch dans `CHANGELOG.md` sur la branche du correctif, puis pose le tag du patch sur le commit de fusion et le pousse. `task` ne publie jamais.
124. Le workflow `.github/workflows/release.yml` part au push d'un tag `v*`. Il contrôle le tag, extrait la section de la version dans `CHANGELOG.md`, construit le livrable, puis crée la release avec ces notes et les fichiers joints. Ses permissions sont `contents: write`, plus `id-token: write` quand il publie sur un registre. Le skill qui clôt n'a qu'à pousser le tag.
125. `release.yml` vérifie d'abord que le tag `vX.Y.Z` vaut la version lue dans `fichier_version`. S'ils diffèrent, il échoue avec un message qui donne les deux valeurs, et rien ne se publie.

### Livrable

126. La fiche de chaque type d'application dans `references/types/` dit ce que la release publie :
    - cli en Rust : une archive des binaires par système de `systemes`, faite par `cargo build --release` sur ce système et jointe à la release ;
    - cli en TypeScript ou en Python : la publication sur npm ou sur PyPI ;
    - library : la publication sur crates.io, npm ou PyPI ;
    - plugin : le tag et la release suffisent ;
    - api et web-frontend : rien n'est joint, le déploiement porte la livraison ;
    - desktop, mobile, game et data-ml : pas de livrable par défaut. La fiche le dit, et le projet écrit le sien dans `release.yml`.
127. La publication sur un registre passe par la publication de confiance (trusted publishing, jeton OIDC de la CI), sans jeton stocké en secret. Le skill optionnel `wizard` guide la configuration côté registre, que seul l'utilisateur peut faire.

### Déploiement

128. Izanagi ne choisit pas d'hébergeur. `docs/agents/harness.md` reçoit une entrée `deploiement` qui porte la commande de déploiement, écrite par le projet. `init` la demande pour les types api et web-frontend. Pour les autres types, et quand l'utilisateur ne la connaît pas encore, elle vaut « à préciser ».
129. Le workflow `.github/workflows/deploiement.yml` se lance à la main par `workflow_dispatch`, avec en entrée le tag à déployer. Il récupère ce tag et lance la commande de l'entrée `deploiement`. Lancer le workflow vaut approbation, parce que, sur un dépôt privé, l'offre gratuite de GitHub n'a pas d'environnements, et les relecteurs obligatoires d'un environnement ne marchent que sur un dépôt public en Free, Pro et Team. Un dépôt public ou une offre qui les permet peut ajouter un environnement `production` avec relecteurs. Le gabarit ne l'exige pas. Les secrets de déploiement sont des secrets du dépôt, que `wizard` aide à poser.
130. La clôture d'un jalon, ou d'un `fix` publié, propose `gh workflow run deploiement.yml -f tag=vX.Y.Z` et ne le lance qu'avec l'accord de l'utilisateur. Pour revenir en arrière, on relance le même workflow avec le tag précédent.

### Template de PR

131. `init` pose `.github/pull_request_template.md` avec quatre sections. Quoi décrit le changement. Pourquoi lie l'issue. Vérification donne le résultat de `check.sh --complet` et du test manuel. Risque donne le niveau. Les flux `task`, `fix` et `jalon` remplissent les mêmes sections dans le corps de leur PR.

### Dépendances et analyse

132. `.github/dependabot.yml` ajoute l'écosystème de chaque composant, en plus de `github-actions` : `cargo`, `npm`, et pour Python l'écosystème que la section « Faits à lire » retient. Les mises à jour sont hebdomadaires. Les mineures et les patchs se groupent en une PR par écosystème, et chaque majeure a sa PR. La CI vérifie ces PR comme les autres, et l'utilisateur les fusionne. Une majeure qui casse la vérification passe par `/izanagi:task`, sur l'issue ou la PR de Dependabot.
133. L'analyse statique est Semgrep CE, dans un job `analyse` de la CI, avec les règles `p/default` et sans envoi de métriques. Elle tourne en CI seulement, comme l'audit, et `doctor` ne la contrôle pas. CodeQL est écarté parce qu'un dépôt privé doit payer une licence GitHub Code Security pour l'utiliser.
134. Un constat de gravité ERROR fait échouer la PR, et les autres gravités s'affichent sans bloquer. Pour écarter un faux positif, on écrit `# nosemgrep: <règle>` avec la raison en commentaire, comme dans `.gitleaks.toml`. `securite.yml` relance l'analyse chaque lundi, avec l'audit et `gitleaks`.

### Contrat de vérification

135. Règle 12 : un projet dont le type a un livrable, ou dont `harness.md` porte une entrée `deploiement` autre que « à préciser », a un `release.yml`. Une entrée `deploiement` demande aussi un `deploiement.yml`. Dans ces deux workflows, chaque action est épinglée par SHA et chaque job déclare ses permissions.
136. Règle 13 : la CI d'un projet qui a du code a un job `analyse`.

### Migration

137. La migration 0.8.0 ajoute à un projet posé :
    - l'entrée `deploiement` à « à préciser » dans `harness.md` pour les types api et web-frontend ;
    - l'écosystème de chaque composant dans `dependabot.yml` ;
    - la clé `langue_publique=fr` dans `config.env`.

    Elle affiche « à préciser » pour l'entrée de déploiement. `upgrade` repose `ci.yml` (job `analyse`), `release.yml`, `deploiement.yml` quand l'entrée existe, `securite.yml` et le template de PR, en montrant l'écart de chaque fichier au gabarit. `CHANGELOG.md` naît à la première release, sans reconstruire les versions passées.

### Izanagi lui-même

138. Izanagi applique la 0.8 à son propre dépôt. Il reçoit un `CHANGELOG.md` avec une section courte par version de 0.1 à 0.7, tirée des specs et des PR, puis une release GitHub à partir de v0.8.0. Son type est plugin, donc le tag et la release suffisent. Il reçoit aussi le template de PR. Le dépôt n'a aujourd'hui aucun workflow. Il reçoit un job `analyse` si Semgrep CE prend en charge Bash (voir « Faits à lire »).

### Tests et réception

139. Les règles 12 et 13 et la migration 0.8.0 ont leurs tests dans `tests/tools.sh`, comme les existantes. Les gabarits de `release.yml` et `deploiement.yml` sont vérifiés sur un projet généré de chaque type qui a un livrable.
140. À la fusion de la 0.8, une issue de réception par élément est ouverte : changelog et release, livrable, déploiement, template de PR, Dependabot, analyse. Ces essais se font sur le projet de la décision 119, à sa première release.

## Faits à lire

Le plan les vérifie dans la documentation de chaque outil avant d'écrire une commande :

- la publication de confiance de crates.io, de npm et de PyPI, et ce qu'elle demande dans le workflow ;
- l'écosystème Dependabot d'un projet Python géré par `uv` (`uv` ou `pip`), et la syntaxe des groupes ;
- la commande exacte de Semgrep CE en CI : installation, `semgrep scan --config p/default`, seuil de gravité, coupure des métriques compatible avec les règles du registre ;
- la prise en charge de Bash par Semgrep CE ;
- `workflow_dispatch` avec une entrée de tag, et la récupération de ce tag dans le job ;
- l'extraction d'une section de `CHANGELOG.md` en Bash, sans outil externe.

## Hors périmètre

Reportés après la 1.0, à revoir avec ce que montrera le projet de la décision 119 :

- les évals du plugin sur un projet témoin ;
- une CI qui lance la suite de tests d'Izanagi sur son propre dépôt ;
- les migrations de base de données pour les types api et data-ml ;
- des conventions d'observabilité dans les fiches de type ;
- un skill de maintenance périodique (dépendances, dette, issues `securite` ouvertes) ;
- la pile Go ;
- les tests de contrat d'API (#32) et la détection des tests instables (#33) ;
- le fuzzing, les benchmarks, la régression visuelle et l'accessibilité.

Écartés :

- CodeQL (décision 133) ;
- un environnement GitHub protégé exigé par le gabarit (décision 129) ;
- le choix d'un hébergeur par Izanagi (décision 128) ;
- un changelog écrit par chaque PR, qui mettrait en conflit deux PR en parallèle (décision 121) ;
- un changelog rétroactif dans les projets migrés (décision 137).

## Coûts

- La clôture d'un jalon gagne une étape : la section du changelog, que l'utilisateur relit.
- Chaque tag lance `release.yml`. Un cli en Rust se construit sur chaque système cible, et les minutes macOS comptent plus cher sur un dépôt privé.
- La publication de confiance et les secrets de déploiement demandent une configuration que seul l'utilisateur peut faire.
- Dependabot ouvre des PR chaque semaine, à relire et à fusionner.
- Le job `analyse` allonge la CI, et ses constats ERROR peuvent bloquer une PR jusqu'à leur correction ou leur exclusion motivée.
